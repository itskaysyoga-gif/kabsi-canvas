## Behaviour with the book on (test businesses only)

- Capture: free text goes to the intent router with the two request tools ("On it" at 10 seconds). `request_new` runs the typed intake through `extract` (one `MODELS.check` call), then `request_intake_propose` with the WhatsApp message id. One proposal with Save and Change, or two or three readings as buttons. Nothing to read writes nothing.
- A second message before a tap (within 30 minutes) revises the same proposal (`request_intake_revise`, the two texts read together); a message the router sends to a Google tool keeps its meaning.
- Save (the button, or a typed yes while a proposal waits here): `request_intake_get` first, so an expired, saved or dropped proposal is refused before any write; then `request_create` with the tap's WhatsApp message id as the key. An old Save answers "This one is already handled. Nothing changed." and makes no second request. A field that needs a choice is never saved by Save or yes.
- No time is invented: words with no exact time are saved as `requested_window_text` with no `starts_at`.
- Find: `request_find` by a name the message holds (a name the model invents is not searched), `request_get` by number. One question at most ("Which one? Send its number.").
- Words: STOP wins; yes saves only with a proposal waiting here; "closed", "cancel" and "post" alone keep today's meaning; with a number ("closed 1") they show that request and say "Changing a request here is not switched on yet. Nothing was changed." (update is RB-F); a number alone is a request only where the book is on; forwarded text never reaches the book.
- After Save there is no Undo button yet (RB-F); no button is offered that does not work.
