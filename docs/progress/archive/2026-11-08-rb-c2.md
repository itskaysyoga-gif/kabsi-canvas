# RB-C2: request book packs, normalizers, tools, policy, replies and intake adapter (8 Nov 2026)

Task RB-C2 (R-139, `docs/kabsi-3/build-plan.md`), on Rashid's GO. Code only and dark: no migration, no model call, no row written anywhere, nothing under `whatsapp/` imports it (guard test), so no public or WhatsApp behaviour changed and no facts change. Pull request 509.

## What exists, in `supabase/functions/_shared/request-book/`

| Part | Files | What it does |
|---|---|---|
| Packs | `packs/schema.ts`, `packs/salon.v1.ts`, `gym.v1.ts`, `garage.v1.ts`, `packs/index.ts` | Data only. One schema checks every pack: kinds used, a word for every status and outcome of those kinds, services with spellings, fields to extract, 3 to 12 example phrases. A pack may not give a word that claims a fact (booked, available, confirmed), or a dash, an exclamation mark or Arabic script. One spelling means one service |
| Normalizers | `normalize/phone.ts`, `dates.ts`, `digits.ts`, `vocabulary.ts` | Each exports a version and every result carries it. Phone reuses `toE164` with the location's country. A digit group touching a letter (3ali, 7assan, 3am) is never a phone. A number is read only when a whole run of whole groups passes the phone check. Dates read the message time in the location's zone. Failing a check is `unknown`, two readings are `ambiguous` with both listed |
| Tools | `tools/registry.ts` | capture, find, list_open, update (status, confirmation, conversion), correct, summarize. Each declares input schema, roles, risk, approval path, idempotency source and cost class. `checkInput` refuses an unknown field like the database does. Undo is the approval path of update and correct, not a seventh tool (`UNDO_BUTTON`) |
| Policy | `policy.ts` | The table of who may do what, matching `private.rb_rule`, `request_set_status`, `request_correct`, `request_undo`, confirmation and conversion |
| Replies | `replies/index.ts`, `replies/words.ts` | Code builds every reply. Never "booked" or "available". "Confirmed by" only from the record, one phrase per side. A list says it covers only what was entered in Kabsi, shows 15 rows then how many more. Unconfirmed names the missing side. Button messages stay under 1,024 characters, at most 3 buttons of 20 characters. Words come from the pack |
| Intake | `intake/adapter.ts` | One `IntakeAdapter` interface. Typed entry is the first adapter and reads only what code can read (phone, time, services) into the evidence shape of `request_intakes.field_evidence`. Other sources are refused as `unsupported_source` until they have an adapter |

## Rules chosen where the design left room (decisions to confirm)

- Bare hours, no am or pm: 8 to 12 are read as written, 13 to 23 as 24 hour times, 1 to 7 are ambiguous (morning or afternoon, two buttons). "bukra l 10" is tomorrow 10:00 as the design says; "Thursday 3" and "Monday 6" ask. Changing it changes `DATES_VERSION`.
- A weekday is the next one; today's own name, and "next <weekday>", have two readings. A slash date with both numbers up to 12 has two readings.
- Customer confirmation is shown as "Confirmed by the client, as told to staff" in a summary (staff recording what the customer said), shorter in lists.
- The list of shipped packs (`packs/index.ts`) names the pack files, so the trade-word guard treats it as pack side. `packs/schema.ts` is scanned like shared code.
- A phone message that needs more than 200 checks is `unknown` (reason `too_many_candidates`), never a partial answer.

## Found by my own check

An input of 8,000 characters of single digits made the phone reader try every stretch of groups and hang. Windows are now at most 15 digits and at most 200 checks a message, with regression tests for the long inputs of phone, dates and vocabulary.

## Independent review

A fresh agent, given only the diff and the rules (not my reasoning), read the code and ran inputs against it. It found the policy matches the SQL branch by branch, no trade word in shared code, nothing importing request-book, no network, secret or model call, and no copy rule break. It confirmed 22 findings. 21 are fixed in this pull request, each with a test; one is kept as a known limit.

High
1. A time with no day ("Sarah at 3") gave empty button titles. Fixed: titles come from the day or the hour that was written, and a button is never empty.

Medium, all fixed
2. Two numbers written with only a space or hyphen between them read as one (the first won). Now the rest of a run is read too, so both numbers are listed and it is ambiguous.
3. Dates and times read as phones ("15 11 2026 10 30", "2026-11-15 10:30", "10-11-2026 3 pm"). A stretch with a year beside a short group is never tried as a phone. A real number ending in a year-like group still reads.
4. An hour a clock change skips left the other reading looking like what was written ("2:30" became 14:30). Now unknown; an hour a clock change repeats gives two readings.
5. A long list cut its own footer (the note that it covers only what was entered in Kabsi, and "and N more"). Rows shrink now, never the footer; names are clipped to 40 characters.
6. The "still needs a confirmation" headline came from the filter, not the rows. It is only used when every listed appointment is missing one.
7. More than three readings of a time fell through to Save. Now there is no Save while any time or number is unresolved; more than three readings asks for the day and hour.
8. Unknown input names such as `constructor` passed the registry check. Uses `Object.hasOwn`.
9. Required fields of update (by operation), correct, capture, find and summarize were not enforced. They are now, as the database enforces them.

Low, fixed
10. `correctDecision` had no state: a closed request, an erased customer's name and the `confirmations_cleared` flag are now covered.
11. `closedOutcome` left out allowed a reopening of a converted request; leaving it out is now refused.
12. "Tomorrow" was now plus 24 hours; it is the next date on the business's calendar.
13. Policy functions gave an answer for a role that is not a member; they refuse as `not_member`.
14. `formatWhen` threw on a bad time zone; it returns nothing.
15. An Arabic comma or question mark beside a number hid it; only letters count now.
17. "tomorrow 10.30", "10:75" and "24:00" dropped the time silently; a real time is read, an impossible one is unknown.
18. The pack schema only refused stray keys at the top; every level is strict now. The Arabic and dash checks cover the presentation forms, the extended blocks and the other dashes and the full-width exclamation mark.
19. Source files held literal Arabic and dash characters in regexes; all are escapes now (guarded by a grep in this record's checks).
20. A list line said "Confirmed by the client" without "as told to staff"; it says it now.
21. A correction with many changes lost its note about the confirmations first; the note is kept and the changes shrink, with "and N more changes".
22. Timestamps in tool input accepted 31 February and a time with no offset; a real date and an offset are required.

Kept as a known limit
16. The phone reader stops after 200 checks in one message, so a very long paste of digit groups before the real number is unknown (reason `too_many_candidates`), never a partial answer.

## Not done, by design

No extraction call (RB-D), no WhatsApp wiring (RB-E), no pack rows or settings, no real customer data. The wiring rule of PR B stands: actor and location come from the verified sender, never from message text. Packs hold a car as a text detail only; vehicles are a later module.
