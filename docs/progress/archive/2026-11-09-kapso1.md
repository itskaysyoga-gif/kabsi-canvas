# Kapso 1 (9 Nov 2026): the daily check of the WhatsApp number and templates

Branch `claude/kapso1`. Read only: no template was created, edited or deleted, the webhook was not changed, no message was sent. The Kapso connector was not used (R-49); the check uses the existing `KAPSO_API_KEY` and `KAPSO_PHONE_NUMBER_ID` Supabase secrets from inside the `health` function.

## What was built

- `supabase/functions/_shared/whatsapp/templates.ts`: `SENDABLE_TEMPLATES` (name, language, category, the parameters the code fills, and which name replaces which), `SENDABLE_NAMES`, `assertSendable`. Built from the `TEMPLATES` table, so it cannot drift from it.
- The guard: `assertSendable` runs in the live sender (`kapso.ts`) and the mock sender (`deliver.ts`). A name outside the list throws `template_not_listed`. `template-check.test.ts` also scans every non-test `.ts` under `supabase/functions` for a `kabsi_...` string that is not on the list (proved to fail with a planted `kabsi_bogus_template`).
- `supabase/functions/_shared/whatsapp/template-check.ts`: the comparison and the once-a-day alert, pure, with injected reads.
- `kapso-admin.ts`: `readTemplateDetails` (GET only: name, status, category, language, body parameter count) and `countParams`.
- `supabase/functions/health/index.ts`: `POST {"only":"kapso"}` with the cron secret. The answer holds names and states only.
- `staff-alerts.ts`: the ops event kind `whatsapp_check` is urgent, so it goes to the staff phone on WhatsApp (R-64).
- Migration `20261109120000_kapso1_daily_check.sql`: one pg_cron job, `kabsi_whatsapp_check`, 05:17 UTC daily. Additive.

## What the check compares

- Number: status, display name status, quality rating, messaging limit, webhook verified (Kapso's own `checks.webhook_verified`).
- Each listed template: exists, status APPROVED, category UTILITY, language `en`, and the same number of body parameters as the code fills.
- Raises (one ops event a day, key `whatsapp_check:<UTC date>`, so `ops_events.dedupe_key` keeps one): a template that is not approved, missing, in the wrong category or language, or with the wrong parameter count; quality YELLOW or RED; a messaging limit lower than the highest in the stored hourly readings (`whatsapp_number_health`, 90 days); a webhook reported not verified; and a Kapso read that fails (a check that cannot read must not pass).
- Number status and display name status are read and reported, not alerted (the display name "Kabsi" is waiting for Meta, PROGRESS ladder).

## Decision to confirm (lane R)

A template that is not in use is reported but never alerted: a first name whose replacement (v2 or later) reads APPROVED and UTILITY is only the fallback (`sendName` in `templates.ts`), and a replacement that is not ready is not sent. Alerting on those would raise a daily alert for states the sender already works around. The check's idea of "in use" is tested against `sendName` for every replacement and every status.
