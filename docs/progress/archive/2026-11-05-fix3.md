## Part A (Sentry KABSI-EDGE-J, 5,850 events since 28 Oct)

Cause: `api/jobs.ts` gave the Coach's `read` dependency straight to `coachRead`, so `refreshCoach(job.location_id)` passed Kabsi's own business id. Google got `.../v1/<uuid>?readMask=profile,categories` and answered 404. The two test personas (Harbour Lane Coffee, Juniper Hair Studio, `is_demo`, `locations/demo-...`) went live too, because the demo check (`googleModeFor`) reads the Google name, and a uuid is not one. A failed read left `coach_read_due` true, so it repeated every 5 minutes.

Fix:
- `COACH_READ.read` reads `google_location_id, concierge, is_demo` and goes through `coachTarget` (`_shared/coach/refresh.ts`): no name or concierge reads nothing; a demo reads the mock. This is how sync (`listReviews(loc.google_location_id)`), Protection (`readProtection(loc.google_location_id)`) and `profileIdentity(googleLocationId)` already call the Google layer.
- `coachRead` refuses anything that is not `locations/<id>`.
- `gbp` name guard (`googlePathOk`): the path after the API base must be an account, a location (alone or under its account) with a known sub-collection or custom method, or a documented collection (`accounts`, `categories`, `v1/media/<ref>`). Uuid-shaped, `demo-`, `concierge-` ids and dot segments are refused. A refusal throws `GoogleNameRefused` (a `PermanentJobError`, no retry) before the gate, the token and fetch, and is reported to Sentry at most once a day (`app_settings.google_name_refused_day`), with uuids written as `<uuid>` in the message so one shape is one issue.
- Migration `20261105130428_fix3_coach_read_wait.sql`: `coach_read_failures`, `coach_read_failed()`, `coach_read_due` replaced with the same rules plus a 24 hour wait after a failure. A read that cannot be saved also counts as failed. Applied with apply_migration (version 20261105130428), read back: the table exists, RLS on, `authenticated` cannot run `coach_read_failed`.
