## 2. What changed in the Sunday job (no new schedule, no new workflow)

- `scripts/backup/backup.sh`, new step "1b" after the repository bundle: mirror clone of `kabsi-harvey-run` and `kabsi-harvey`, `git bundle create --all`, `git bundle verify`, encrypt with age (the same `seal`), each in the manifest with its ref count and HEAD sha. Then the release assets of `kabsi-harvey-run` by REST (`gh api`): every release, every asset, copied as they are to `weekly/<stamp>/harvey-release/<tag>/<asset>`. Only a file that ends in `.enc` and starts with the openssl `Salted__` header is copied; anything else is deleted on the runner and named in a warning. The manifest has a `harvey` block (repos, release assets with sizes and sha256, skipped). The staff summary gets the counts.
- `HARVEY_READ_TOKEN` (new, optional, read only): missing, expired or refused is a warning and the job succeeds. Documented in `docs/SECRETS.md` and `docs/OPS-SETUP.md` step 9. The token reaches git through `GIT_CONFIG_*` and gh through `GH_TOKEN`, never a command line, and every message that could carry it passes `scrub`.
- A pull request run gets no `HARVEY_READ_TOKEN`; its dry run uses `scripts/backup/harvey-fixtures.sh` (two tiny repositories, a stub gh, a stub release with one plain file that must be refused), so the whole Harvey path runs on every pull request.
- Storage: the Supabase CLI printed one line per downloaded file in the log of a public repository, and some names hold a phone number (a WhatsApp voice note id). Its output now goes to a file; a failure prints only lines that name no file. The old run logs still hold those names (Manual steps).
- `docs/SECRETS.md`: new rows `HARVEY_READ_TOKEN`, `HARVEY_DB_KEY`, `HARVEY_SOURCE_TOKEN`, and `QA_SMOKE_TOKEN` (the workflow reads it and the file did not name it); the knobs row now lists the new settings and says 3 sets, matching the script.
- `restore-drill.sh` is unchanged: it walks `manifest.files`, so it also checks and decrypts the two new bundles (about a minute more).
