## Part A: suggestions through kabsi.co (PR 454)

- `POST /api/suggest` (`src/routes/api.suggest.ts`, logic `src/server/suggest.ts`, wiring `src/server/suggest-deps.ts`): `warm`, `pass` and `suggest`, the same request and answer as profile-snapshot.
- Places Autocomplete (New) is called from `supabase/functions/_shared/google/places/autocomplete-web.ts`, inside the Google layer; the session token rules are unchanged, and the chosen place's Details call still ends the session.
- Protections, by the visitor's own address (Vercel's x-forwarded-for):
  - Turnstile once, then the same 15 minute pass (same visitor hash and HMAC as profile-snapshot);
  - at most 10 bot checks a minute per visitor per instance;
  - 20 a minute, 120 an hour and 60 a day plus `places_take('autocomplete')`, in one call to `public.suggest_take` (same keys as profile-snapshot), with a 3 s abort.
- The database and Google run at the same time only for a visitor this instance saw allowed in the last 30 s with no call in flight; otherwise the database goes first. After any refusal, the instance goes database first for a minute.
- Cache: 10 minutes per normalised prefix and country, in memory and in Vercel's Runtime Cache (SHA-256 keys, the key stored with the list and checked on read). Nothing personal is in it.
- Server-Timing: `bot`, `cache`, `db`, `google`, `total`. One log line per call: `fn`, `status`, `outcome`, `cache` and `ms`.
- Client (`src/lib/suggest-route.ts`): the route first; profile-snapshot on 503 `not_configured`, 404 or 403, and for one call on any other 5xx. The 200 ms debounce, the last list kept, late answers ignored and the in-flight call cancelled are unchanged (business-combobox.tsx untouched).

### The database call (Rashid's yes in this session)

- Every way for the route to reach the database met a guard:
  - the service key breaks `tests/sec1-service-role.test.ts`;
  - an anon-callable SECURITY DEFINER function breaks `rls_functions.sql` test 3;
  - a dedicated Postgres login role was built and then dropped. On this project PUBLIC can use pg_net's schema, its request queue and response tables (all owned by supabase_admin, so they cannot be revoked here), so any login role could read the queued requests with the cron secret header.
- Rashid chose the route key. The migration made a 32 byte key in Vault (`suggest_route_key`). `suggest_take` is reached with the public key and refuses every call without that key, and a refused call counts nothing. `rls_functions.sql` test 3 now names `suggest_take` as anon's only exception.
- Migration `20261106150353_speed2_suggest_take.sql`, applied with apply_migration. Read-back:
  - anon can execute it, authenticated cannot;
  - it is security definer;
  - 1 Vault row;
  - no login role left.
- Live refusal: PostgREST `rpc/suggest_take` with the public key and a wrong key answered `{"code":"P0001","message":"suggest_take: not allowed"}`.
- Supabase's security advisor lists this one function as anon-executable SECURITY DEFINER (the approved exception, LATER row).

### Independent reviews (fresh agent, the diff and the rules only)

- Round 1, all fixed:
  - High: a burst on a fresh instance, or at the cap, could start Google calls the cap never counted.
  - Medium: the Runtime Cache's default key hash is 32 bit (collisions, planted lists).
  - Low: no limit before Turnstile.
  - Doubts acted on: the origin check now compares hosts, and the client falls back on 403 and 5xx.
- Round 2, all fixed:
  - High: the login role reached pg_net. That design was dropped for the route key.
  - Low to medium: no client-side database timeout.
- Left for lane R: the 10 minute cache of Google's lists (LATER row).
